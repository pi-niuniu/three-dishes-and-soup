## 总体结论
**修改后可用。** 选云开发（CloudBase）是对的，但方案有四处硬伤：成本说法不准，个人主体能不能做 UGC 没核实，数据模型和现有 `Dish` / `MealHistoryRecord` 对不上，安全和并发也基本没设计。补完这几块再开工。

## 问题清单
严重｜方案二·选型表 / 一·5“零成本”｜云开发已经没有永久免费额度，最低套餐大约 ¥19.9/月（具体以官网为准）。套餐到期环境会停服，`db.watch` 长连接和图片 CDN 流量也要计费｜把“零成本”改成“低成本”，写明套餐和流量预算。另外要有停服预案：云端不可用时自动退回纯本地模式

严重｜阶段四 / 背景约束·个人主体｜个人主体小程序带“用户上传图文”功能，审核常被以“个人主体不支持用户发布内容”驳回。方案没有评估这一点｜加一个“阶段0”先核实合规。私房菜只在家庭内可见，不能公开分享；同时准备退路：只存本地或只录文字，或者换成个体工商户主体

严重｜阶段四·3｜`imgSecCheck` 已废弃｜改用 `security.mediaCheckAsync` 加消息推送回调，文本用 `msgSecCheck` v2（要带 openid 和 scene）。两者都在云函数里调用。审核结果出来前菜品标记 `pending`、只有本人可见；检测不通过就删掉云存储里的文件

严重｜三·2 `families` / 阶段五·1｜让前端直接写 `memberOpenids` 的话，安全规则拦不住有人把自己加进别人家庭。另外 `users.familyId` 和 `memberOpenids` 存了两份，容易不一致｜加入、退出、解绑全部走云函数并用事务，在事务里校验人数上限（2 人）。安全规则用 `get('database.families.${doc.familyId}')` 校验调用者是否成员

严重｜三·4 `custom_dishes` vs `types/dish.ts:43-70`｜缺推荐引擎必需的字段：`cookingMethod`、`spicyLevel`、`mainIngredient`、`availableMonths`、`regions`、`difficulty` 等。分类也漏了 `egg` 和 `tofu`｜录入页只让用户填少量字段，其余用服务端默认值补齐（比如全年可做、地区“全国”）。id 统一加 `custom_` 前缀，避免和现有菜品 id 撞车

严重｜阶段三·1“优先读云端”｜`historyService.getHistory()` 是同步方法，有 8 个以上页面在直接调用。改成云端优先就得全面改异步，而且弱网下首屏会卡｜改成“本地缓存优先”：同步 API 不变，云端在后台增量拉取后回写本地。离线写入先进 outbox 队列，带重试，并且写操作要幂等

一般｜三·3 `meal_history`｜两人各自生成菜单会得到不同的 `menuId`，同一顿饭会记成两条。字段也和 `types/user.ts:20` 不一致（`dishes` 和 `dishIds`，`menuId` 缺失）｜`_id` 改成确定性的 `${familyId}_${date}_${slot}`，用 `set` 做 upsert，规则定为“后写覆盖 + 保留 confirmedBy”。字段对齐现有的 `dishIds`/`dishNames`，再加一个 `thumbUrl` 快照

一般｜三·2 `inviteCode`｜6 位码可以被暴力枚举，码直接存在 families 文档里，前端可能读到。分享卡片被转发到群里，任何人都能加入｜单独建一个 `invites` 集合，邀请码单次有效、24 小时过期。云函数里限制尝试频率，人满（2 人）就拒绝。如果说要“签名 token”，签名密钥只能放在云函数里

一般｜三·2 `sharedPreferences`｜“辣度取交集”说法含糊。`preferenceService` 的上云和合并没有排进任何阶段｜辣度取两人最小值，忌口和黑名单取并集，收藏仍按个人。更新用 `_.addToSet` 按字段改，别整对象覆盖

一般｜阶段二·2 解绑｜没定义解绑后数据归谁｜建议：历史记录双方各留一份快照。私房菜归录入者，跟着录入者走。最后一人退出时，家庭数据保留 30 天后清理，连同云存储文件一起删

一般｜阶段四·4｜`dataProvider` 在构造函数里同步初始化，私房菜是异步加载的。历史里引用的私房菜被删后，`getDishById` 会返回 undefined｜私房菜先缓存到 Storage，启动时同步合并，后台再刷新。展示历史时，找不到菜品就用快照兜底

一般｜阶段四·2｜图片的大小、路径、压缩都没有规定｜上传前用 `chooseMedia` 加 `compressImage` 压缩，长边 ≤1080、大小 ≤300KB。路径用 `families/{familyId}/dishes/{uuid}.jpg`

一般｜阶段五｜漏了账号注销、隐私协议更新（相机/相册/昵称头像）和本地历史迁移｜补上“注销并删除数据”入口。昵称头像用头像昵称填写能力（`chooseAvatar` 等），不用 `getUserProfile`。首次绑定时把本地历史合并上云

建议｜一·3“秒级同步”｜家庭场景用不着一直开着 watch 长连接，费用和连接数都划不来｜默认在页面 `onShow` 时拉取，只在历史页按需开 watch

建议｜一·2 单人使用｜单人和双人走两套代码会分叉｜登录后自动建一个只有自己的“单人家庭”，单人、双人走同一条代码路径。不登录也能正常点菜

建议｜四·分阶段｜没有灰度发布和回滚开关｜加一个 `cloudEnabled` 功能开关，先在体验版里自己家用两周，再提审

## 做得好的地方
1. 选型比较的维度很清楚，排除自建服务器和纯前端两种方案都有充分理由。云开发方案也延续了 `technical-design.md` 里原本规划的“本地 + 云端”双层架构，方向一致。
2. 阶段拆分顺序合理（先身份 → 再绑定 → 再同步 → 最后 UGC）。风险最高的上传功能放在最后，单独出问题也不会拖垮整体交付。
